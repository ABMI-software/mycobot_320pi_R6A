Gazebo_to_LeRobot_Pipeline — internal runbook

Sandbox /home/tomislav_ilic/tomislav/robotics/Gazebo_to_LeRobot_Pipeline Host Ubuntu 26.04, WSL2, ~4.8 GB usable RAM, CPU-only Reproduced via Docker (Ubuntu 24.04) Commit 157041d on main Written 2026-09-12

Overview & architecture

Why this exists, why it's built the way it is, and the one constraint that shapes every decision below.

The host laptop runs Ubuntu 26.04, which has no official ROS2 Jazzy or Gazebo Harmonic packages. The team's own mycobot_320pi_R6A repo — the digital twin this sandbox reuses — targets exactly Jazzy + Harmonic on Ubuntu 24.04. Rather than fight the host OS, Gazebo_to_LeRobot_Pipeline runs the whole stack inside one Ubuntu 24.04 Docker container, with WSLg's X11/Wayland sockets and /dev/dxg GPU device bind-mounted in, so Gazebo, RViz and rqt_image_view render out to the host desktop like native apps.

One container stays running for the life of a session (docker/run.sh, once), and every terminal after the first attaches to it with docker/shell.sh. ROS2's DDS discovery is unreliable across separate containers/network namespaces — one shared container sidesteps that class of problem entirely rather than working around it per-command.

The digital twin — mycobot_description and mycobot_gateway — is a one-time copy from the team repo, not a live bind-mount: this sandbox is meant to be a decoupled, disposable place to learn Gazebo and prove the pipeline, not a second working copy of the main project. Three files in that copy were hand-modified (lower controller update-rate, smaller/partly-disabled camera sensors, a longer controller-switch timeout); those three are tracked on their own under overrides/ rather than duplicating the ~130 MB mesh tree — see Git & reproduction.

The resource ceiling that shaped every call in this document: this VM has roughly 4.8 GB of usable RAM and no GPU compute, only WSLg's D3D12-translated rendering. Headless Gazebo, 320×240 cameras, and stopping short of an actual SmolVLA training run are all direct consequences of that ceiling, not oversights.

The pipeline, step by step

Each step is a real dependency of the next — this is the order a fresh reproduction has to follow. Every step pairs how it's done with the concrete check that proves it worked, not just that a command exited zero.

01

Build the Docker image

Produces gazebo_to_lerobot:jazzy-harmonic — Ubuntu 24.04 + every package in the tool inventory above.

Procedure

cd Gazebo_to_LeRobot_Pipeline
docker/run.sh   # builds the image, then starts the container

Or build alone: docker build -t gazebo_to_lerobot:jazzy-harmonic -f docker/Dockerfile docker.

Verify

  • docker images lists gazebo_to_lerobot:jazzy-harmonic.
  • The build log reaches rosdep init / rosdep update with no unresolved apt package names.

If apt-get hangs mid-build without ever failing outright, that's environment bug #1 in Bugs fixed — environment, not a Dockerfile defect.

02

Start the persistent container

One long-lived container with WSLg's display/audio sockets and GPU device bind-mounted in, so GUI tools render to the host desktop.

Procedure

docker/run.sh     # first time only
docker/shell.sh   # every subsequent terminal

run.sh mounts /tmp/.X11-unix, /mnt/wslg, /usr/lib/wsl, passes --device=/dev/dxg, forwards DISPLAY/WAYLAND_DISPLAY/PULSE_SERVER, and bind-mounts src/ so host edits are visible without a rebuild.

Verify

  • docker ps shows gazebo_to_lerobot running.
  • Inside a shell, glxinfo | grep "OpenGL renderer" reports a real renderer (D3D12 translation or software), not an immediate GL context failure.

If the GUI window is black or GL init fails outright, the documented fallback (not needed in practice here) is -e LIBGL_ALWAYS_SOFTWARE=1 on the terminal that runs Gazebo's GUI.

03

Import the digital twin

Snapshot-copy the team's mycobot_description and mycobot_gateway packages, then re-apply three sandbox-specific edits.

Procedure

Copy (not symlink) both packages from mycobot_320pi_R6A into src/mycobot_R6A/, then apply the three files under overrides/ on top:

  • controller.yaml — update_rate 500 → 100 (WSL2 virtualization jitter).
  • mycobot_pro_320_pi_gazebo.urdf — the 3 secondary cameras (right/left/top) set <always_on>false</always_on>; all 4 cameras' resolution 640×480 → 320×240.
  • mycobot_teleop.launch.py — adds a headless launch arg, raises controller --switch-timeout to 60s, and pushes the spawner start delays to 8.0/8.5/9.0s.

Verify

  • diff overrides/<file> src/mycobot_R6A/<same path> is empty — the override is exactly what's live.
  • grep -c always_on src/mycobot_R6A/.../mycobot_pro_320_pi_gazebo.urdf shows 3 occurrences set to false.
  • At launch time (step 5), the controller_manager log reports an update rate of 100 Hz, not 500.
04

Build the workspace

colcon-build every package under src/ inside the container.

Procedure

cd /workspace
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash

Verify

  • colcon build exits 0 with all packages reported Finished.
  • ros2 pkg list | grep -E "mycobot|Gazebo_to_LeRobot_Pipeline" lists all four: mycobot_description, mycobot_gateway, gazebo_to_lerobot_bringup, mycobot_moveit_config.
05

Bring up sim + control graph

Spawn the robot in Gazebo Harmonic, activate its controllers, and bridge one camera — headless by default.

Procedure

ros2 launch gazebo_to_lerobot_bringup sim_full.launch.py
# add headless:=false for the GUI window, all_cameras:=true for all 4

sim_full.launch.py wraps mycobot_gateway/mycobot_teleop.launch.py target:=sim — the one reused launch file that actually spawns joint_state_broadcaster + mycobot_controller + gripper_position_controller and bridges /clock — and adds the ros_gz_image image_bridge node(s) it doesn't set up on its own.

Verify

  • ros2 topic list shows /clock, /joint_states, /gz/joint_states, /synth_camera/image(/compressed), /mycobot_controller/joint_trajectory.
  • ros2 topic hz /joint_states reads ≈150 Hz, matching joint_state_broadcaster's configured publish_rate.
  • ros2 control list_controllers shows joint_state_broadcaster and mycobot_controller both active.
  • ros2 run rqt_image_view rqt_image_view, select /synth_camera/image, shows a live picture of the arm.
06

Command the arm directly

Prove the controller path works with no MoveIt2 in the loop, by publishing one raw trajectory point.

Procedure

ros2 run gazebo_to_lerobot_bringup send_test_trajectory \
  --positions 0.3 -0.2 0.2 0.0 0.0 0.0 --duration 4.0

Publishes a single trajectory_msgs/JointTrajectory point to /mycobot_controller/joint_trajectory with the 6 arm joints in controller.yaml's order.

Verify

  • The arm visibly moves in Gazebo (GUI mode) or in rqt_image_view (headless).
  • ros2 topic echo /joint_states converges to the commanded positions within --duration. Confirmed run: target [0.65, 0.20, 0.15, 0.15, 0.15, 0.15] matched exactly in the echoed joint states.
07

Continuous keyboard teleop

Drive the arm live, one small trajectory point at a time, for recording demonstrations later.

Procedure

ros2 run gazebo_to_lerobot_bringup teleop_arm_keyboard

Seeds its start position from the first /joint_states message (no jump on launch), then publishes a fresh short-horizon point every 0.1 s: q/a w/s e/d r/f t/g y/h for joints 1–6 ±0.05 rad, o/c gripper, z home.

Verify

  • Holding a key drives smooth continuous motion (spline interpolation between closely-spaced targets), not discrete jumps.
  • /joint_states tracks the displayed running target — confirmed live by the user against on-screen target values.
08

Plan & execute with MoveIt2

Hand-authored MoveIt2 config (no upstream one existed) targeting the same mycobot_controller action interface.

Procedure

ros2 launch mycobot_moveit_config move_group.launch.py
ros2 launch mycobot_moveit_config moveit_rviz.launch.py   # separate terminal

Drag the interactive marker in RViz and hit Plan & Execute — or skip RViz and call the action directly: ros2 run gazebo_to_lerobot_bringup send_moveit_goal, which builds joint constraints for all 6 arm joints via moveit_msgs/MoveGroup.

Verify

  • Action result error_code.val == 1 (SUCCESS).
  • /joint_states after execution matches the goal — confirmed on a real planned motion.

Group arm is a 6-joint chain base→link6; self-collision is blanket-disabled (all 171 link pairs) — a deliberate simplification for pipeline verification, not collision-aware planning.

09

Import & configure the rosetta bridge

Pull the 5-repo rosetta/LeRobot ecosystem and declare which ROS2 topics map to which LeRobot dataset keys.

Procedure

vcs import src < src/rosetta.repos
colcon build --symlink-install --packages-up-to rosetta lerobot_rosetta

The contract at src/contracts/mycobot_320_pi.yaml maps observation.images.front to /synth_camera/image/compressed, and both observation.state and action to /joint_states — a deliberate deviation from rosetta's leader/follower examples, since this sandbox has no physical leader arm; action records what the sim arm achieved, not a command issued an instant earlier.

Verify

  • ros2 pkg list includes rosetta, rosetta_interfaces, lerobot_rosetta, lerobot_teleoperator_rosetta, lerobot_robot_rosetta.
  • episode_recorder_node starts against the contract with no schema errors.
10

Record a teleoperated episode

Capture a rosbag2 recording of a teleop session, structured per the contract.

Procedure

Run episode_recorder_node (or episode_keyboard_node for start/stop control) against the contract, while driving the arm with teleop_arm_keyboard from step 7.

Note the sim's real-time factor is well below 1.0 even headless — a "5-second" episode at the contract's 30 fps takes noticeably longer than 5 real seconds to perform.

Verify

  • ros2 bag info <bag> lists the contract's topics (/joint_states, /synth_camera/image/compressed) with message counts consistent with the episode's duration and rates.
11

Convert the bag to a LeRobot dataset

rosetta_port turns a bag + contract into a LeRobot v3.0 dataset directory.

Procedure

# system Python, ROS sourced, venv's site-packages prepended --
# see upstream bug B below for why the installed console script
# can't be run directly
PYTHONPATH="$VENV/lib/python3.12/site-packages:$PYTHONPATH" \
  python3 -m rosetta.robots.ros2.offline.port \
  --bag <bag> --contract src/contracts/mycobot_320_pi.yaml \
  --out datasets/mycobot_320_pi_test

Verify

  • Output directory has the LeRobot v3.0 layout: parquet episode files, AV1 video, info.json, stats.json, tasks.parquet.
  • No conversion errors or dropped frames reported.

Level 3
Stopped here
Actually instantiate the SmolVLA policy and run a training smoke test

Fixed on the way: missing accelerate (lerobot-train's [training] extra); a validation error requiring repo_id for push_to_hub (fixed with --policy.push_to_hub=false). Stopped at a missing transformers package — lerobot[smolvla]'s extra, which would pull in the ~500M-parameter SmolVLM2 vision-language backbone.

This dataset was never meant to teach SmolVLA anything useful — 2 episodes of scripted keyboard motion with no real task semantics (no red block, no goal condition) — its purpose was purely to prove the pipeline end to end. Given that, and the VM's ~4.8 GB RAM / CPU-only ceiling, pushing into an actual backbone download and forward pass was judged very likely to fail on resources rather than reveal anything new, and was deliberately not attempted, per the user's explicit standing instruction to stop rather than push through near-impossible resource constraints.

Bugs worth reporting upstream

Two defects that reproduce independent of this VM — real bugs in code other teams depend on. Filing the actual GitHub issues has not been done and needs a separate explicit go-ahead.

Silent !!python/tuple serialization corrupts nested-list parametersNot yet filed

Candidate repo: ros2/launch_ros (or wherever its Node parameter-file writer lives — not pinned down to an exact file/line this session)

Symptom
Passing a Python dict with nested list values to Node(parameters=[{...}]) gets written to a generated temp params file with PyYAML !!python/tuple tags. ROS2's own parameter parser can't read that tag, so the value comes back empty or misread — with no error raised anywhere. In this project it surfaced as move_group aborting with "Planning plugin name is empty or not defined in namespace 'ompl'", even though the launch file's ompl_planning dict clearly listed planning_plugins.
Fix used here
Wrote ompl_planning.yaml and moveit_controllers.yaml as real standalone /**:\n ros__parameters: files and passed their paths as strings, instead of Python dicts, in parameters=[...].
Why it matters
This is silent data corruption in a widely-used launch API — any Node with a nested list inside a dict parameter is at risk, with no error to point at the cause. A plausible fix is a custom YAML representer that dumps plain lists instead of tuples.

Installed rosetta_port console script can't honor its own recommended venvNot yet filed

Candidate repo: iblnkn/rosetta

Symptom
The installed rosetta_port script's shebang is #!/usr/bin/python3 (system Python), and it resolves its entry point via importlib.metadata, which only sees packages installed into system Python. rosetta's own docs recommend installing lerobot[dataset,async] into a separate venv — but the installed script's shebang bypasses whichever venv is active in the shell entirely, so it can never import lerobot as shipped.
Fix used here
Located the real entry point (rosetta.robots.ros2.offline.port:main, found via the package's own egg-info entry_points.txt) and invoked it directly with system Python, ROS environment sourced, with the venv's site-packages prepended onto PYTHONPATH — see step 11 above.
Why it matters
The documented install workflow (separate venv for the lerobot deps) and the packaging (a system-Python console script) actively contradict each other — anyone following the README's own instructions hits this.

Git & reproducing this from scratch

This sandbox is a local git repo, not yet pushed anywhere — sharing it with the team on GitHub is a deliberate future step, not done here.

Repo root Gazebo_to_LeRobot_Pipeline/, branch main, initial commit 157041d (28 files, ~160 KB — no meshes, binaries, venvs, or build artifacts). The file manifest below shows exactly what's tracked.

Two things are intentionally not tracked, because they're either reconstructible or someone else's code to own:

  • src/mycobot_R6A/ — copied from mycobot_320pi_R6A (step 3); ~130 MB of mesh assets that belong to that repo, not this one. The 3 hand-modified files live in overrides/ instead.
  • src/action/ — the 5 rosetta-ecosystem repos, cloned via vcstool (step 9); pinned upstream code, re-cloned rather than committed.

A teammate cloning this repo fresh needs, in order: this repo; read access to mycobot_320pi_R6A for its mycobot_description/mycobot_gateway packages; then:

git clone <Gazebo_to_LeRobot_Pipeline repo> && cd Gazebo_to_LeRobot_Pipeline
# 1. reconstruct the digital twin (step 3)
cp -r <mycobot_320pi_R6A>/mycobot_description src/mycobot_R6A/
cp -r <mycobot_320pi_R6A>/mycobot_gateway     src/mycobot_R6A/
cp -r overrides/mycobot_description/* src/mycobot_R6A/mycobot_description/
cp -r overrides/mycobot_gateway/*     src/mycobot_R6A/mycobot_gateway/

# 2. build the container (step 1-2)
docker/run.sh && docker/shell.sh

# 3. inside the container: rosetta ecosystem (step 9) + build (step 4)
vcs import src < src/rosetta.repos
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install && source install/setup.bash

# then steps 5-12 as documented above
