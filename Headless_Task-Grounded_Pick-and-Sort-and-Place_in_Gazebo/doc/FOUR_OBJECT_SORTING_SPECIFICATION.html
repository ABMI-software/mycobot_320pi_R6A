Part 0 — Scope and reading guide

0.1 What this specification covers

This document specifies the acquisition of sixty task-grounded pick-and-place episodes in the project’s four-object, four-bin Gazebo world, recorded in LeRobot format, verified per episode, and split into a training set and a held-out-condition validation set.

It is written to be executed end to end by one person on one machine.

0.2 Who performs the work, and on what

One person performs every step in this document: the specification artefacts, the configuration, the scripts, the verification logic, the smoke test, the acquisition batch, any graphical verification and the report, all on one Windows laptop running WSL2. Hardware, measured on 2026-10-04:

PropertyValue

At that real-time factor a 25-second episode takes about 73 s of wall clock for its motion; a full episode, bring-up and verification included, took a median of 160 s, and the 60-episode batch about 2.7 hours (Appendix C).

0.3 Provenance of the inputs

The premises this specification is built on were gathered in preparation and are recorded in Part 1 as an explicit assumption register, not woven into the narrative. Each one is stated, explained, traced to what depends on it, given a cheap verification procedure, and given a fallback if it proves false.

This structure is deliberate. Several of the premises are second-hand, one pair of them is mutually inconsistent, and at least one — if true — materially improves the deliverable. Treating them as assumptions rather than as settled fact is what makes the specification safe to execute without further clarification.

Where this document needs a decision that only the wider group can make, it says “refer to the robotics team”. Those points are collected in Appendix B.

0.4 Files are local

All world files, model files, launch files and the reference pipeline named in this document are assumed present on the local filesystem of whoever is executing the step. No repository synchronisation procedure is specified. If a named file is absent, that is an assumption failure — see Part 1, A3.

Part 1 — The assumption register

Twelve assumptions. Each carries a verification that costs minutes, and a fallback. Work through them in order before starting Part 2; the register is the cheapest part of the project and the one that prevents the expensive mistakes.

A1 — A merged world containing four objects and four colour-matched bins exists

Statement. A Gazebo world file exists on disk containing four graspable objects and four destination bins, colour-matched one-to-one.

Two candidate paths are in circulation, and they are inconsistent. One premise names mycobot_description/worlds/pick_and_place_sorting.sdf as the target and describes it as containing exactly the four objects and four bins. A second premise states that the four objects were added to the photorealistic, ArUco-calibrated world derived from real_table.sdf, and explicitly characterises pick_and_place_sorting.sdf as the older generic 4-object world.

These cannot both describe the target. One describes a world that exists; the other may describe an intent.

What depends on it. Everything. Object poses, bin poses, table height, the reachability envelope, the camera topic names, the visual realism of every recorded frame.

Verification. Part 2 in full — roughly two hours.

Fallback. If the ArUco/photorealistic world contains only one object-bin pair while the generic world contains all eight, then merging the four objects into the ArUco world is itself a work item, and a substantial one. Refer to the robotics team the same day, with the enumeration from Part 2.3 attached as evidence.

A2 — The object and bin set is fixed and colour-matched

Statement. The four objects are red_cube, blue_cube, green_cylinder, yellow_box. The four destinations are red_bin, blue_bin, green_bin, yellow_bin. Each object belongs in the bin of its own colour.

Explanation. These names correspond to eight physically 3D-printed and hand-coloured parts, and to the eight classes of the team’s object detector (cube_rouge, cube_bleu, cylindre_vert, pave_jaune, bac_rouge, bac_bleu, bac_vert, bac_jaune). The Gazebo model names are the English equivalents of the detector class names. This correspondence is not incidental — it is the reason the instruction vocabulary in Part 5 should be adopted rather than invented.

Note the shape heterogeneity. Two cubes, one cylinder, one box. This is not four instances of one problem; see Part 4.1.

What depends on it. The instruction set, the object manifest, the per-object grasp parameters, the verification logic.

Verification. Part 2.3’s model enumeration lists exactly these eight names.

Fallback. If the names differ, adopt whatever the world actually declares and propagate through config/objects.yaml — nothing else hardcodes them.

A3 — All world, model and pipeline files are present on the local filesystem

Statement. The world SDF, the eight model SDFs, the ArUco marker models, the table camera definition and the reference launch pipeline are real files on disk — not screenshots, not planned work.

Explanation. This assumption is what permits this specification to omit any synchronisation procedure. Every command in this document reads local paths.

Verification. Part 2.2’s find sweep locates each of them. Any file that does not appear is an assumption failure.

Fallback. Missing files are reported to the robotics team as a blocking gap, naming exactly which artefacts are absent. Do not reconstruct a model from a presentation image — a reconstructed object has the wrong dimensions, the wrong mass and the wrong friction, and every downstream number inherits those errors invisibly.

A4 — A reference pipeline achieving a physically-verified grasp exists locally

Statement. A launch file — named in the premises as sim_grasp.launch.py, under a mycobot_gateway package — loads this world and, together with a companion node, performs a grasp in which the gripper closes for real and the result is checked against Gazebo’s own object pose, explicitly described as not teleportation.

Why this assumption deserves its own evaluation. The previous acquisition spent two working days attempting a rigid-body friction grasp and did not achieve one. It fell back to an explicitly labelled DetachableJoint weld, and that weld is the single largest caveat on the resulting dataset — a model trained on it learns approach, close, carry, open, not the physics of grasping.

If A4 is true, that caveat can be retired at the cost of reading someone else’s working code, rather than at the cost of another physics-tuning campaign.

Interaction with A8. A separate premise states that the simulated attachment remains the sanctioned mechanism. These are not in conflict. The sanction against further physics tuning was issued in response to a request made after two days of failure; it is a refusal to authorise more tuning, not an instruction to ignore a working mechanism that already exists. Part 3 resolves this with a one-day bounded evaluation and a written decision.

What depends on it. The single most consequential caveat in the dataset README, and therefore the scientific value of the sixty episodes.

Verification. Part 3 in full — one day, hard cap.

Fallback. A8 applies unchanged: the labelled weld, with four attachment configurations.

A5 — The demonstrator may use ground-truth object poses

Statement. The recording script is permitted to read object positions directly from the simulator rather than detecting them from camera images.

Explanation, because this is widely misunderstood. A vision-language-action model learns the mapping instruction + image → action. During training it observes the recorded images, the recorded language and the recorded actions. It never observes how the demonstrator knew where the object was. The demonstrator is an oracle whose only job is to produce correct, clean trajectories; the provenance of its knowledge is not part of the training signal.

Consequently the demonstrator is allowed to “cheat” by querying gz model -p. This is standard practice in scripted-demonstration data generation, and it saves an order of magnitude of effort relative to closing a perception loop that contributes nothing to the recorded data.

What it does not license. It does not license recording ground-truth poses into the observation stream. The observation contains images and proprioception only. If ground-truth object poses leak into observation.*, the model will learn to read them and will fail catastrophically at inference when they are absent. Keep them in the episode metadata, never in the observation.

What depends on it. The entire architecture of the spawn and sequence scripts, and the absence of any perception component from this work.

Verification. Inspect the rosetta contract: observation.state must contain joint positions and the gripper only. Part 10.1.

Fallback. If camera-driven acquisition is later required, that is a separate work item with its own specification; it is not a variation on this one.

A6 — Sorting assignment is by colour

Statement. Each object goes to the bin of its own colour. Assignment is not by size, shape, or any other property.

Explanation. This resolves an ambiguity inherited from earlier work on the physical bench, where two cartons of different sizes were distinguished by area and associated with ArUco-tagged destinations. That size-based logic belongs to a different task and must not be carried into this one.

What depends on it. The instruction strings, the expected-bin field in every episode’s metadata, and the wrong-bin check in Part 9.2.

Verification. Self-evident from the model names once A1 and A2 are confirmed.

A7 — ArUco IDs 10 and 11 are not sorting destinations

Statement. The markers with IDs 10 and 11, which appear in earlier hand-crafted detection work as identifiers for a large and a small carton, play no role in this task.

Explanation. The four ArUco markers relevant to this world carry IDs 19, 23, 25 and 26, and they serve extrinsic camera calibration, not sorting. Confusing the two sets would attach meaning to markers that carry none here.

What depends on it. Nothing functional — but it prevents a category of wasted investigation.

Verification. grep -o 'aruco_[0-9]*' <world.sdf> | sort -u returns 19, 23, 25, 26 and nothing else.

A8 — The simulated attachment remains sanctioned

Statement. Carrying the object by an explicitly labelled DetachableJoint weld, triggered on gripper close and released on gripper open, remains acceptable for this acquisition.

Explanation. This is the mechanism used in the previous acquisition. It is labelled SIMULATED ATTACHMENT in code comments, in log lines, and in every episode’s metadata file. It is honest, it is reproducible, and it removes an entire class of non-convergent tuning from the critical path.

Its cost, stated plainly. No slip. No compliance. No grasp-failure examples. A policy trained on this data cannot learn when a grasp will fail, because the dataset contains no failures of that kind.

Interaction with A4. A8 is the floor, not the ceiling. If Part 3 shows a physical grasp is available essentially for free, taking it is strictly better and should be reported as an improvement.

A9 — Target volume is fifteen clean successful episodes per object

Statement. Sixty episodes total, fifteen per object, where clean successful means the episode passed every check in Part 9. Failed attempts are re-run, not counted toward the fifteen.

Explanation. The distinction matters for scheduling. At the measured real-time factor (Part 0.2), and allowing for bring-up, settle time and a realistic retry rate, sixty clean episodes is about three hours of wall clock. A naive reading of “sixty episodes” that counted failures would finish sooner and deliver less.

What depends on it. The episode matrix in Part 6, and the batch scheduling in Part 11.

A10 — The acquisition batch runs on a machine with memory headroom

Statement. The sixty-episode batch executes on a machine with enough memory to run the full stack without pressure: the laptop of Part 0.2, where three full simulator stacks at once still left 4.75 GB available.

Explanation, in two parts.

Duration. About three hours at the measured real-time factor of 0.344. The 0.082 measured on the memory-constrained machine of the previous acquisition would make it about four times longer.

Correctness. This is the stronger argument. The previous acquisition, run on a memory-constrained machine, produced documented symptoms of memory exhaustion: robot_state_publisher terminated and presenting as “TF loss after prolonged uptime”; move_group stuck in executing after a peer was killed; container restarts destroying an installed virtual environment twice; and — decisively — a pair of physics measurements that cannot both be true. A gripper tip offset of 0.105 m was recorded as “touched the object”; 0.100 m as “never touched it”. Lowering a target by five millimetres cannot cause contact to cease. That was memory pressure wearing the costume of physics, and two days were spent tuning contact geometry against a simulator being dismembered underneath the experiment.

A four-object, four-bin world has substantially more collision pairs than the single block and static plate of the previous acquisition. Running the batch without memory headroom does not risk being slow. It risks being wrong in a way that looks like data.

What depends on it. The whole of Part 11.

A11 — The runtime environment matches the previous acquisition

Statement. Every step executes inside the same container image — Ubuntu 24.04, ROS 2 Jazzy, Gazebo Harmonic — as used for the previous headless acquisition.

Explanation. This is the reproducibility guarantee, and it is what makes moving the work to another Windows host tractable at all. The container is the contract; the host supplies CPU, RAM, disk and a display.

What depends on it. preflight.sh in Part 11.6, and the credibility of the statement “it runs the same on your machine”.

Verification. preflight.sh checks ROS distribution, Gazebo presence, ros_gz_sim, moveit_py, pyarrow and ffmpeg before any batch begins.

Residual risk, to be stated rather than hidden. Every artefact from the previous acquisition ran gz sim -s. Display passthrough from a container to a Windows host is the one class of problem that scripting does not anticipate; on WSL2 it needed DISPLAY=:0 and software OpenGL. Part 11.8 specifies how to handle this honestly.

A12 — The 0.63 mm figure is not the benchmark for this work

Statement. The end-to-end positioning figure of 0.63 mm from the team’s precision campaign is not the target against which this acquisition, or any policy trained on it, should be measured.

Explanation. That figure is the converged accuracy of a closed-loop classical pipeline after two visual correction passes — 10.79 mm open loop, 1.29 mm after one correction, 0.63 mm after two, with 18 of 20 trials under 1 mm. It measures how precisely a system converges on a commanded metrology point when permitted to look, correct and look again.

A vision-language-action policy does none of that at inference. It emits actions from pixels and language, open loop, with no metrology target and no correction cycle. Holding it to a servoing figure measures a different quantity and reports the mismatch as failure.

What replaces it. Part 13 specifies the correct metric set. The headline: correct-bin rate, because it is the only metric that distinguishes a policy that reads the instruction from one that ignores it.

Where 0.63 mm does belong. In the comparative analysis of the current production architecture, quoted honestly as what it is.

3.6 If the weld is retained — the four-configuration trap

Each of the four objects needs its own attachment configuration, and every one must target link6, never gripper_base.

Why, and why it is silent. gripper_base is a TF/URDF frame only. The URDF-to-SDF conversion folds it into the link6 Gazebo link, so it does not exist as an addressable Gazebo link name. A DetachableJoint declaring child_link: gripper_base accepts the attach message and does nothing — no error, no warning, no log line. The symptom is identical to a genuine friction-grasp failure: the object does not move. The previous acquisition lost a full debugging cycle to exactly this. With four objects there are now four opportunities to repeat it.

Validate all four at authoring time, before the batch:

Part 4 — Step 3: Object and bin geometry

4.1 Four objects is not four times one object

Two cubes, one cylinder, one box. The differences are load-bearing.

The cylinder has no opposed flat faces at arbitrary yaw. A parallel-jaw gripper closing on a cylinder makes line contact rather than surface contact, and the object remains free to roll about its axis. If a physical grasp was adopted in Part 3, the cylinder is the case most likely to fail — test it first, not last. If the weld was retained, the cylinder costs nothing, which is a legitimate secondary argument for the weld in this dataset.

The box has a long axis. The gripper must close across its short dimension. This requires a per-object wrist yaw, which the previous acquisition never needed because a cube is rotationally symmetric under a top-down grasp.

The two cubes are presumed identical in shape. Verify rather than presume — a differing edge length changes the grasp height.

4.6 Why grasp height is measured from the object centre

For a cube of edge a whose centre sits at height z, the top face is at z + a/2. Aiming the fingertips at z would drive them through the object. Aiming at z + grasp_dz with grasp_dz slightly less than a/2 places the finger pads around the upper portion of the object.

For the cylinder, grasp_dz must be below length/2 so the pads contact the curved wall rather than closing above the top face — a failure mode observed directly in the previous acquisition, where a grasp height of 0.12 m left the object completely undisturbed.

This is the single number most likely to need adjustment, and the cheapest to change. It lives in objects.yaml for exactly that reason.

Part 5 — Step 4: Task definition and instruction vocabulary

5.1 The instruction becomes load-bearing — this is the point of the exercise

In the previous acquisition, all twenty episodes carried one instruction: “pick up the red block and place it on the plate.” There was one object and one destination.

A policy trained on that data could discard the language stream entirely, learn “move to the one red thing, close, move to the one white thing, open”, and score 100%. The dataset could not distinguish a model that reads instructions from one that ignores them. Every episode was consistent with both hypotheses.

With four objects present in every frame and four instructions, that is no longer true. A policy ignoring the language can do no better than chance — 25%. The instruction now carries exactly two bits, and the dataset can measure whether the model uses them.

That is the difference between demonstrating a pipeline and producing data with a learnable signal in it. It is also why Part 13’s headline metric is correct-bin rate.

5.2 All four objects appear in every episode

This requirement is what makes 5.1 true, and it is easy to violate by accident.

Every episode spawns all four objects and all four bins. The instruction names one object. The other three are distractors, and their positions are randomised independently per episode.

If only the target is spawned, the previous acquisition has been rebuilt four times and nothing has been learned. If the distractors are always in the same place, the model learns “the red cube is always at the left” rather than “find the red cube”.

5.3 Adopt the existing vocabulary

The team’s object detector is trained on eight classes: cube_rouge, cube_bleu, cylindre_vert, pave_jaune, bac_rouge, bac_bleu, bac_vert, bac_jaune. The Gazebo model names are the English equivalents.

Use instructions that map one-to-one onto those classes. Do not introduce synonyms — not “the red block”, “the crimson cube”, “the red container”. One phrasing per object, byte-identical across all fifteen of its episodes.

Paraphrase robustness is a deliberate later experiment with its own held-out design. Introducing variation now, by accident, makes it impossible to run that experiment cleanly later.

6.3 Why a held-out condition, not held-out images

This is not a formality, and the project has direct in-house evidence for it.

The markerless pose-estimation work failed because the model memorised two fixed camera mounts rather than learning to localise. It performed well on held-out images from those mounts and collapsed on an unseen mount. Holding out images tests memorisation of pixels; holding out conditions tests generalisation.

The team’s own object-detector evaluation follows the same principle — full detection on the training camera, degraded detection on a camera never seen during training, reported honestly as a snapshot rather than a measured rate. This held-out split is the established practice, not an import.

Part 7 — Step 6: Inverse kinematics and waypoints

7.1 What carries forward unchanged

Solve IK locally, command joints. The manufacturer’s Cartesian interface measured 247.8 mm final error against 18.2 mm for joint commands plus differential IK, on an identical 267 mm target — and it failed silently, returning success from the bridge either way. The cause was gimbal lock with RY between −78° and −83°. Never use it.

Force the elbow-up branch. Reject any solution with J3 >= 0 and re-seed. Historical poses are elbow-down against the J2 limit with zero margin, which produces 150° branch jumps on J4 under closed-loop control.

Approach from directly above, always. The team’s own campaign measured the cost of mixing approach directions across four sides: 5.918 mm of spread, against a worst single-side repeatability of 0.84 mm. Approach direction costs roughly seven times the worst repeatability. Every descent in this dataset comes from above, without exception. This is not a preference; it is a measured constraint, and it is also — see Part 12 — a constraint a learned policy does not inherit automatically.

7.2 The gripper frame, re-measured

The previous acquisition lost a full debugging cycle here. With four objects, there are four chances to repeat it.

  • The IK target frame is gripper_base, not link6
  • Fingertips sit approximately 0.10 m below gripper_base
  • The fingers meet approximately 0.036 m ahead of gripper_base — the frame is not symmetric between the fingers

So the Cartesian target for a grasp is not the object centre. It is the object centre displaced by the fingertip vector, expressed in gripper_base.

Re-measure in this world rather than copying, because the gripper attachment may differ:

7.5 Branch consistency across the whole episode

J3 < 0 per solve is necessary but not sufficient. The sequence must stay on one branch. A branch flip between LIFT and TRANSPORT produces a large wrist rotation mid-carry, which flings a physically-grasped object and, either way, looks bizarre in the recorded frames — teaching the policy a motion no sensible controller would produce.

The 0.6 rad per-joint, per-waypoint threshold in check_waypoints.py catches this. If a sequence fails, re-seed that episode’s solve rather than lowering the threshold.

7.6 If a position cannot be solved

Change the position in the matrix and regenerate. Do not let the batch discover it at runtime, and do not relax the elbow-up requirement to make a stubborn position solve — an elbow-down episode in an otherwise elbow-up dataset is a contaminant.

Three reasons; the third is the one that bites.

  1. Descending into the bin drives the finger pads against the bin walls
  2. A short drop settles the object flat rather than balanced on an edge
  3. If the weld is in use, detaching while the object is in contact with the bin floor can produce a solver impulse — the same class of event that punted an object 4 cm laterally in the previous acquisition. Detach in free space and let it fall three centimetres.

9.2 The check this task requires and the previous one did not

Was it the right bin?

The previous acquisition had one destination, so “placed” and “placed correctly” were the same question. They are now different, and the wrong-bin failure is invisible to every check in 9.1: the object was grasped, carried, and released into a bin. Every numeric criterion passes. The episode is wrong anyway, and the instruction attached to it is false.

An episode with a false instruction is worse than no episode. It teaches the model the opposite of the task, and it does so with the same confidence as a correct one.

# scripts/checks.pyimport mathdef placed_in_correct_bin(target, cfg, obj_pose, tol=0.005):    """Inside its OWN bin footprint, and below the rim — not resting on it."""    b = cfg["bins"][cfg["objects"][target]["bin"]]    dx, dy = obj_pose[0] - b["pose"][0], obj_pose[1] - b["pose"][1]    inside  = math.hypot(dx, dy) <= (b["inner_radius"] - tol)    settled = obj_pose[2] <= b["rim_z"]    return inside and settled, {"inside": inside, "below_rim": settled}def landed_in_wrong_bin(target, cfg, obj_pose):    """Explicitly detect the silent failure."""    own = cfg["objects"][target]["bin"]    for bn, b in cfg["bins"].items():        if bn == own:            continue        if math.hypot(obj_pose[0] - b["pose"][0],                      obj_pose[1] - b["pose"][1]) <= b["inner_radius"]:            return bn    return None

9.3 Were the distractors disturbed?

An episode in which the gripper knocked the blue cube across the table while fetching the red one is a poor demonstration: the frames show motion the instruction does not describe.

def distractors_undisturbed(target, start_poses, end_poses, tol=0.02):    moved = []    for name, p0 in start_poses.items():        if name == target:            continue        d = math.dist(p0[:2], end_poses[name][:2])        if d > tol:            moved.append([name, round(d, 4)])    return (not moved), moved

Treat a disturbed distractor as a warning, not a hard failure. Record it; decide at dataset-assembly time whether to exclude. Real demonstrations contain incidental contact. What must never be recorded is a mislabelled episode.

10.2 Recorder bring-up, with the fixes already paid for

Three hard-won details from the previous acquisition:

Use the non-daemon lifecycle form. The ros2 lifecycle CLI reports “node not found” for a recorder that has in fact started, because of a stale daemon cache. This cost three failed attempts and roughly 1 h 49 min on a single episode.

ros2 lifecycle set --no-daemon --spin-time 15 /episode_recorder configureros2 lifecycle set --no-daemon --spin-time 15 /episode_recorder activate

Never use the bare form.

Never wait on an exit-marker file alone. A watcher that polls only for a success sentinel cannot distinguish “still working” from “process killed”, and it will always report the reassuring one. The previous acquisition lost an entire night to a watcher polling for a marker that a dead process would never write.

wait_for() {                       # usage: wait_for <pid> <marker> <timeout_s>  local pid=$1 marker=$2 deadline=$(( $(date +%s) + $3 ))  while [ ! -f "$marker" ]; do    kill -0 "$pid" 2>/dev/null || { echo "PROCESS DIED before marker"; return 2; }    [ "$(date +%s)" -gt "$deadline" ] && { echo "TIMEOUT"; return 3; }    sleep 2  done  return 0}

Bound every step. Each ros_gz_sim create gets a 90 s timeout; each attempt gets a 25-minute watchdog; the recorder configure step is retried once with a 60 s cap. A normal attempt takes about 3 minutes on the laptop of Part 0.2.

10.3 Per-episode clean restart

Restart the whole simulation stack for every episode. It costs bring-up time and it buys reproducibility. The previous acquisition documented move_group entering a stuck executing state after a leftover trajectory, silently failing every subsequent motion — a restart is the only reliable remedy, and detecting the condition mid-batch is harder than avoiding it.

11.3 Why memory headroom is not optional

11.8 Be honest about what cannot be guaranteed

The pipeline cannot be promised to work on hardware it has never run on. What can be promised, and should be said in these terms:

Part 12 — What this does not prove

Volunteering the limits is what makes the rest credible.

If the weld is retained: the carry is not a grasp. A policy trained on this learns approach, close near the object, carry, open — not the physics of grasping. It is labelled in code, in logs, in every episode’s metadata and in the README.

If a physical grasp is adopted: it is still rigid-body contact with tuned friction. The physical gripper is an adaptive unit that stalls on the object at an angle that is not the commanded one — 52° measured for a command of 20°. None of that is modelled.

The demonstrator used ground-truth poses. Correct and deliberate — but it means the dataset contains no perception failures, no partial-occlusion recoveries, and no cases where the object was not where the camera believed it to be. Real deployment contains all three.

Object selection was scripted, not perceived. The demonstrator always reaches the correct object because it was told which one. The policy must learn selection from pixels and language, but the dataset contains no examples of a demonstrator hesitating, disambiguating or correcting. Selection is the hard part of this task, and the data shows only its solved form.

Two limitations a learned policy inherits that the classical pipeline does not. Both are first-party measurements from this project:

  • Approach direction. Mixing approach directions costs 5.918 mm, roughly seven times the worst single-side repeatability. The classical pipeline avoids this by construction — it always descends from above. A policy emitting Cartesian or joint actions has no such guarantee and will reproduce whatever the demonstrations contained. Constraining the action space, or enforcing unidirectional approach at recording time, is not optional.
  • Frame corruption. One camera frame in sixty arrives corrupted and reports a position 17.5 mm wrong. The classical pipeline defends with a six-frame median, taking worst-case error from 17.5 mm to 0.8 mm. A policy consuming single raw frames at inference has no such filter and will act on the bad frame.

Sim-trained data carries a visual domain gap. The project’s own pose-estimation result is the evidence: 10.9% real-image detection from synthetic-only training, rising to 91.6% only after mixing real data with ×5 oversampling. Mixing beats scaling, and that applies here.

Sixty episodes is not a training set. The community figure for fine-tuning is 100–500 episodes per task. This is four tasks × fifteen. It is a smoke test with real semantics and a real held-out condition, not a dataset ready to train on.

What it does prove, precisely: that the pipeline produces task-grounded episodes in the project’s real ArUco-calibrated world, with four distinct instructions whose language is load-bearing, verified per episode including correct-bin placement, split against an unseen condition — and that all of it except the batch run itself is feasible on commodity hardware.

Part 13 — What to measure

13.1 Why the 0.63 mm figure is the wrong target

Per A12. That figure is the converged accuracy of a closed-loop classical pipeline after two visual correction passes — 10.79 mm open loop, 1.29 mm after one correction, 0.63 mm after two, with 18 of 20 trials under 1 mm. It measures how precisely a system converges on a commanded metrology point when permitted to look, correct and look again.

A vision-language-action policy does none of that at inference. It emits actions from pixels and language, open loop, with no metrology target and no correction cycle. Holding it to a servoing figure measures a different quantity and reports the mismatch as failure.

Its legitimate place is as the measured performance of the current production architecture — the system a learned policy would eventually have to match or complement — quoted honestly as what it is.

13.3 Why correct-bin rate is the headline

It is the only metric that distinguishes a policy that reads the instruction from one that ignores it. A policy discarding the language stream ceilings at 25% — chance across four bins. No millimetre figure can reveal that, and it is the precise question the four-object exercise exists to make answerable.

Report it alongside overall success rate, never instead of it: a policy can achieve high grasp success and chance-level bin selection, and those are very different failures with very different remedies.

C.4 Findings the specification did not anticipate

  • Gazebo renders a camera only when it has a subscriber: an unsubscribed camera costs nothing, which first made rendering look free.
  • WSL's GPU rendering path draws every runtime-spawned object white; software OpenGL renders the colours.
  • type="ode" does not select ODE in Gazebo Harmonic: the engine actually used is DART.
  • The low RTF comes from the robot's 14 triangle-mesh collision shapes (bench alone RTF 1.000, with the robot 0.220): primitives are the next iteration's largest win.
  • Folded lift poses are obstructed when an object is welded: zero error unloaded, error on J3 loaded, insensitive to mass. Objects near the base are outside this dataset until fixed.
  • A cube lands at the gripper's world yaw at release, mod 90°: the closing jaws square it to the gripper.
  • Bins are axis-aligned squares: three bugs came from modelling them as circles (gap, path clearance, keep-out).
  • A dataset's timestamps must come from header (simulation) time. Bag receive time stretched an episode's 20.6 simulated seconds over 106.8 s of wall clock; a loader that seeks video by timestamp then returns the wrong frame without raising an error.

Appendix E — Training SmolVLA on the sort recordings, evaluating it, and making each evaluation recomputable (added 2026-10-30)

E.1 Goal

Appendix D produced training data: Osama's four-object sort, one episode per pick-and-place, in LeRobot and RLDS formats. This appendix specifies what was planned and done with that data from the filing of PR #25 (2026-10-11) to 2026-10-30:

  1. train the SmolVLA vision-language-action model on it, on Kaggle's free T4 GPUs;
  2. measure, with protocols fixed before each measurement, whether the trained policy uses its cameras to find the pieces;
  3. evaluate it in the tri_yolo Gazebo scene in the format of the ROS2SmolVLA paper (arXiv 2608.23320): pick, place and place after a successful pick, in distribution and out of distribution;
  4. make every Gazebo evaluation recomputable: any piece of a batch run, successful or not, can be run again later, with the Gazebo window open, and must give the identical result, step by step, with policy and physics both recomputed (not replayed).

The record of what was measured, step by step with the commands, is the report's addendum of the same date (sections 44–58). This appendix states the plan, the rules and the definitions of done, and Part E.9 lists what is not done yet.

Stop conditions of Run C (the driver stops and says GUARD STOP; the run is not resumed): auxiliary loss above 1 at any step up to 50; more than 5 of the first 100 updates skipped by the fp16 loss scaler; the scaler below 1,024 after step 100; a checkpoint whose head is not identical to its warm start.

Midway rule (run_c_midway_stop): between the two sessions of Run C, the probe and the image-swap test run on the step-5,000 checkpoint; the second session runs only if the encoder does not localise worse than smolvla_base and the policy still uses its images.

E.6 Step 4: measurements that decide, each fixed before it is run

  1. Open-loop check (open_loop_check.py): recorded frames of the held-out seeds 91–100 go through a checkpoint, and each predicted 50-action chunk is compared with the recorded actions over the same steps: gripper-tip distance (forward kinematics), joint error, gripper error, and the distance between the predicted and the recorded close. 120 chunks (starts at frames 0, 60, 120) over 40 episodes; paired comparisons between checkpoints with 95 % intervals from 2,000 resamples of whole episodes (open_loop_compare.py).
  2. Image-swap test (--swap-images): each episode receives the camera images of the same piece on the next seed, with its own state and instruction. A policy that uses its images moves its grasp toward the image donor's grasp. Criteria: the grasp-point shift and the change in the share of closes nearer the donor, both with the lower end of their 95 % interval above 0.
  3. Encoder probe (probe_render.sh, probe_features.py, probe_fit.py): 799 full-frame renders of layouts 5001–5800; a linear (ridge) probe on each camera's connector output predicts the four pieces' x, y; 5 folds by layout; median and 90th-percentile error in mm; paired bootstrap against smolvla_base; floors (mean position, raw pixels) and a ceiling (true image position). Variants fixed in addenda before they were run: cropped renders (crop_test), intermediate layers (layer_probe).
  4. Run C gate (run_c_gate): a Run C checkpoint goes to Gazebo only if its encoder localises better than smolvla_base (by more than 5 mm and 20 %, interval excluding 0, on at least 2 of 3 cameras: at most 25.6 / 31.0 / 30.9 mm) and it passes the image-swap test.
  5. Final Run C report (run_c_final_report, amended 2026-10-27 before any checkpoint past 5,000 existed): the grasp is judged on a grasp-focused open-loop set: 5 chunks per held-out episode starting 30, 25, 20, 15 and 10 frames before the recorded close, 200 chunks, the recorded close inside every one. Run C 10,000 is compared with Run B 20k (same data, both at the end of their learning-rate schedules) and with Run B 10k (equal samples). "Better localisation became better grasps" only if the grasp-point interval lies entirely below 0, at least 100 of the 200 chunks are paired, and Run C does not close in fewer chunks than Run B minus 10.

Definition of done: each result written in probe_protocol.yaml under the rule it was judged by, with its numbers, and committed.

E.7 Step 5: Gazebo evaluation in the format of the ROS2SmolVLA paper

  1. Runner. eval_tri_seed.sh <checkpoint> <seed> <out dir> starts the tri_yolo scene headless and runs eval_smolvla_tri_sort.py. For each piece, the arm goes to the observation pose (out of distribution) or to the recording's random start (in distribution), the gripper to −0.28, then the policy drives: Gazebo is paused while the policy computes a 50-action chunk, then the actions are played at 10 Hz of simulation time; at most 300 steps per piece.
  2. Scoring from Gazebo's ground truth, which the policy never sees: picked when the piece rises above 6 cm; placed when it ends within 47 mm of its own bin's centre, below 6 cm; place after pick = placed among the picked pieces (conditional, as in the paper).
  3. Conditions. Out of distribution: seeds 11–20, all four pieces, observation start. In distribution: seeds 1001–1040, the recorded target only, the same pre-placed pieces and the recorded random start (PREPLACE=1, which re-runs the deterministic preplacement and checks it against the recording's preplaced.json).
  4. Failure modes per piece (failure_modes.py): sorted; picked, not placed; never closed; closed in the air; memorised spot (closed within 20 mm of a training grasp, away from the piece); wrong place; near miss.
  5. Table (paper_table.py): pick, place and place-after-pick, in distribution, out of distribution and overall, with 95 % Wilson intervals, next to the paper and to the 13/10 model.

Definition of done: 50 seeds evaluated (10 out of distribution, 40 in distribution), the table and the failure modes recorded.

E.8 Step 6: recomputable evaluations (step-locked mode)

A repeat of the one successful out-of-distribution piece of Run B (seed 17, yellow box) in the Gazebo window did not reproduce it: 0.02° of difference at the start grew to 13 mm one chunk later. The cause is not the physics engine (DART is deterministic) but everything that lets wall-clock timing into the simulation. The plan, in five parts, all opt-in (STEP_LOCKED=1), the earlier mode unchanged:

  1. Step-locked loop (scripts/step_lock.py, eval_smolvla_tri_sort.py --step-locked). Gazebo never runs freely after start-up: it advances exact blocks of 1 ms steps (multi_step, each block sent only when the previous one is done), commands are sent while it is paused, observations are taken on the cameras' 10 Hz ticks from frames stamped exactly then, moves last a fixed number of steps, PyTorch runs deterministically, and the simulation time is read from Gazebo's own /stats, not from the ROS /clock. The server starts paused and the robot is spawned at simulation time 0, so the 100 Hz controller loop and the cameras share one time grid.
  2. Viewer window (VIEWER=1): the same headless server as a batch run, plus a gz sim -g window that only displays it; the policy's images are always rendered by the headless server.
  3. Fingerprints: per piece, SHA-256 of the start snapshot, the start state, every step's state and action, the piece poses and every camera frame the policy saw (compare_runs.py reports identical, or the first step and quantity where two runs part).
  4. Exact state reset at the start of every piece (scripts/gz_systems/state_reset.py, a Python Gazebo system): a snapshot of the 12 robot joints, the gripper command and the four pieces' poses, taken by the batch run (or loaded from it, RESET_FROM), is put back to the bit with zero velocities; the joints' velocity command is zeroed before the physics step, the reset is repeated over the 10 steps up to a controller update, the controllers receive identical hold commands, and one camera tick earlier the scene is moved "far" so that the renderer redraws everything at the exact reset. From there the run depends on nothing that happened before; one piece can be recomputed alone (repeat_eval_gui.sh <run dir> [piece]).
  5. Recording and playback (RECORD=1, play_eval_gui.sh): Gazebo's state every 20 ms of simulation time, played back without recomputing.

Rule for every message in the loop: it either cannot be lost, or a loss stops or delays the run; never "the run continues with old data". Arm and gripper commands (whose controllers subscribe BEST_EFFORT) are sent three times while paused and read back after the first controller update of every action period: the gripper's six commands in the controller manager's introspection must equal the command sent exactly, the arm's trajectory must give the points sent at its first, middle and second-to-last point (query_state). The joint state the policy reads comes from Gazebo itself (state request to the reset plugin, with Gazebo's simulation time). Images are used only when stamped exactly on the current tick. A missing or different read-back stops the run with an error.

Tests and definitions of done:

  • Test A: seed 17 run step-locked (A1), then recomputed from A1's snapshots (A2): every piece identical (fingerprints of start, images, joint states, actions and piece poses at every step).
  • Test B: seed 17 recomputed from A1's snapshots on the same headless server with the viewer window: identical to A1.
  • Test C: an in-distribution seed (1001) run twice: identical.
  • Then the 50-seed paper comparison of Run B 20k again, step-locked, so that every piece of it, successful or not, can be recomputed in the window with the same result.
