Headless_Task-Grounded_Pick-and-Place_in_Gazebo — implementation report

Task-grounded pick-and-place, headless, from spec to twenty recorded episodes

What was built against doc/headless_pick_and_place_specification.md, step by step, with the verification used for each step, every bug found along the way, and exactly where the delivered mechanism deviates from what the specification assumed — most importantly, that the grasp is a simulated attachment, not rigid-body contact physics.

Sandbox ~/tomislav/robotics/Headless_Task-Grounded_Pick-and-Place_in_Gazebo Host Ubuntu WSL2, ~4.9 GB usable RAM, CPU-only Reproduced via the gazebo_to_lerobot Docker container (Ubuntu 24.04, ROS2 Jazzy, Gazebo Harmonic) Commit 5c92a565 on main Written 2026-09-22

Overview

This document is the implementation report for headless_pick_and_place_specification.md — the file in this same directory that was treated as a binding specification of design and verification goals, not of implementation details. Per the governing instruction under which this work was done, specific programming choices in that document were free to be replaced with better solutions; every goal had to be either achieved or explicitly reported as a problem.

The short version: every numbered step in the specification (Parts 1–8) was implemented and verified, twenty LeRobot-format episodes were recorded and split into a 15-episode training set and a 5-episode held-out-camera validation set, and the pipeline is fully self-verifying (a CSV-based pass/fail check runs at the end of every episode). The one load-bearing deviation is in the grasp mechanism itself: after a deliberate, bounded physics experiment produced no friction hold, the block is carried by a Gazebo DetachableJoint weld triggered on gripper-close and released on gripper-open — labelled SIMULATED ATTACHMENT, NOT a physical grasp everywhere it appears, in code comments, log lines, and every episode's own metadata. Four bugs were fixed in the arm-and-gripper sequencing path, three more in the recording-batch infrastructure, three more in the demo-launch orchestrator added on 2026-09-22 (§13–15), and four are flagged as worth reporting upstream.

Addendum, 2026-09-22 (§13–15): a manager asked for a single ros2 launch entry point to actually run and watch this demo, rather than the 7-step manual walkthrough (§manual) that was the only way to run it before. Two launch files now wrap one orchestrator script, with gui, record, block_x/block_y and attach_mode exposed as ordinary, documented ros2 launch arguments — attach_mode deliberately, so the simulated-attachment limitation is visible at the point of use, not only in this document.

This report follows the same structure as the runbooks in Gazebo_to_LeRobot_Pipeline/docs/ and ROS2_to_RLDS_Conversion_OpenVLA/docs/: a step-by-step account pairing what was done with the concrete check that proves it, a reference section for bugs and limitations, and a manual, human-runnable walkthrough at the end.

The implementation, step by step

Twelve steps, in the order they had to happen. Each pairs what was done with the check that proves it, and calls out where a bug was found and fixed along the way.

01

Author the block and the plate

Two standalone SDF models, spawned at runtime — nothing added to the world file, everything reversible.

Procedure

models/red_block.sdf and models/plate.sdf, copied from the specification's own Parts 1 and 4 essentially unchanged: block mass 0.05 kg, 0.04 m cube, diagonal inertia 1.333e-05, friction μ=μ2=1.5, contact kp=1e6/kd=1.0; plate a static 0.06 m-radius, 0.008 m-thick cylinder.

The block's contact stiffness and a DetachableJoint plugin were added later (§8–9) — this step is the pure-spec baseline.

Verify

gz sdf -k models/red_block.sdf
gz sdf -k models/plate.sdf

Both print nothing (valid) — the spec's own definition of done for step 1, met exactly.

02

Spawn headless and verify the pose

Two independent checks, per spec Part 3: numeric pose and a visual camera frame.

Procedure

ros2 run ros_gz_sim create -world empty -file models/plate.sdf \
  -name plate -x 0.20 -y -0.15 -z 0.044
ros2 run ros_gz_sim create -world empty -file models/red_block.sdf \
  -name red_block -x 0.25 -y 0.0 -z 0.05

scripts/grab_frame.py subscribes to /synth_camera/image/compressed, decodes with cv2.imdecode, saves with cv2.imwrite — adapted almost verbatim from the spec's own sketch.

Verify

gz model --list
gz model -m red_block -p

Confirmed the block settles at exactly (0.250, 0.000, 0.020) in a fresh sim — consistent with the spec's own "Z settles slightly below spawn height is normal" case (half the 0.04 m cube). The saved PNG confirmed the block genuinely red and resting on, not inside, the ground plane.

03

Cartesian IK helper

The one piece of genuinely new code the spec flagged — and the step where two corrections beyond the spec's sketch were required.

Procedure

scripts/ik_helper.py builds a MoveItPy instance and solves with RobotState.set_from_ik("arm", target, TARGET_LINK, timeout=1.0), rejecting any solution with J3 ≥ 0 (elbow-down) and retrying with a random seed, exactly per spec §5.4. Seed chaining across waypoints (each call seeded with the previous solution instead of the default zero pose) keeps a whole sequence on one consistent branch.

Verify

fk_check() cross-checks every IK solution by running forward kinematics on it: FK-of-IK reproduces the requested pose to ≈1e-7 m.

Correction beyond the spec: the sketch's target link is a placeholder name at the fingertip. The real target here is gripper_base, a TF frame whose fingertip offset had to be measured (§7) — targeting link6 or a naive fingertip name drives the real fingers underground. The top-down orientation quaternion is also frame-specific and was derived empirically by commanding a known-good link6 pose and reading gripper_base's resulting orientation via TF, not copied from the spec's (1,0,0,0).

04

Precompute the waypoints offline

A better solution than the spec anticipated: moveit_py and a plain rclpy node cannot coexist in one process on this stack, so IK is solved once, offline, before the sequence ever imports rclpy.

Procedure

python3 scripts/precompute_ik.py \
  --block-x 0.25 --block-y 0.00 --block-z 0.02 \
  --tip-offset 0.105 --tip-dx -0.036 --hover 0.08

Solves home/approach/descend/lift/transport/place/retreat in order, chaining each solution as the next seed, and writes waypoints.json. --poses batch-solves many block positions in one process for the recording batch (§10).

Verify

Printed J1/J3 per waypoint; a batch run is only accepted if every waypoint's J1 stays within ±1.2 rad and J3<0 — the elbow-up, forward-facing branch used for every recorded episode.

Not in the spec, discovered the hard way: constructing MoveItPy in the same process as an explicit rclpy.init()+Node made the MoveItPy constructor hang indefinitely (reproducible across container restarts, ruling out stale DDS state); and separately, letting a MoveItPy instance be garbage-collected tears down its internal rclcpp context and silently breaks any other rclpy activity in that process. See the upstream-bug candidate in §bugs-upstream.

05

Script the pick-and-place sequence

scripts/run_pick_and_place.py — plain rclpy, no moveit_py import, consuming waypoints.json.

Procedure

Ten phases (home → open → approach → descend → grasp → lift → transport → place → release → retreat → home). Each arm move goes through the real MoveGroup action and blocks on its result; move_to_joints_closed_loop re-issues a corrective move (up to 4 times) if the achieved joints differ from target by more than 0.02 rad. The gripper command is republished every 0.5 s while polling /joint_states, and accepts either reaching the target or stalling below −0.1 rad for 2 s (object contact) as success.

Verify

Every phase logs "move OK"/"move FAILED" from the action's own error_code, and a pose snapshot (block xyz, end-effector xyz, dz) is written after every phase — feeding the grasp-proof CSV in §6.

Two more bugs fixed here, neither in the spec: (1) trajectory_execution.allowed_start_tolerance at its default 0.01 in mycobot_moveit_config/launch/move_group.launch.py caused every execution after the first to fail with CONTROL_FAILED/"Apparently trajectory initialization failed" — raised to 0.2, fixed permanently in Gazebo_to_LeRobot_Pipeline. (2) The gripper command was originally published once, which is dropped by the classic ROS2 publisher/subscriber discovery race; fixed by republishing periodically.

06

Prove the grasp numerically

Spec Part 7, implemented as specified — then found to have a real loophole and hardened.

Procedure

A CSV row per phase snapshot: t, phase, bx, by, bz, ex, ey, ez, dz (dz = ee_z − block_z). A lift-peak camera frame is saved via grab_frame.py for visual corroboration, exactly per spec §7.6.

Verify

def grasp_held(rows, tol=0.008, min_rise=0.05):
    lift = [r for r in rows if r["phase"] in ("lift", "transport")]
    ref = lift[0]["dz"]
    constant = all(abs(r["dz"] - ref) < tol for r in lift)
    rose = max(r["bz"] for r in lift) - descend["bz"] > min_rise
    return constant and rose

Loophole found in the spec's own check: the specification's grasp_held() (§7.5) checks only that dz stays constant. A block that never moves at all has a trivially constant dz — and that is exactly what several early runs produced (the gripper closed on empty air beside the block). The check now also requires the block to rise ≥5 cm during lift, which a stationary block cannot satisfy.

07

Where the block actually settles

The finding that explained why early grasp attempts closed on empty air: the spec's nominal spawn coordinates are not where the gripper needs to be.

Procedure

Measured, via TF and gz model -p, at a known-good hover pose with the gripper open: fingertip joint origins sit ≈0.10 m below gripper_base when pointing down, and the finger pair's meeting point in x is ≈0.036 m ahead of gripper_base, asymmetric because left1/right1 sit at −0.048/+0.080 relative to it. precompute_ik.py's --tip-offset 0.105 --tip-dx -0.036 defaults encode these two measurements directly.

Verify

With the correction applied, the gripper's closing fingers made contact with the block for the first time in this project (stalling at a non-zero joint position instead of reaching fully closed) — the first evidence that geometry, not friction, had been the blocking issue all along.

Practical consequence for §2's position-variation range: the elbow-up IK branch has no solution below x≈0.245 once this offset is folded in, which is why the recorded episodes vary x over [0.25, 0.31] rather than the spec's suggested [0.22, 0.28].

08

Attempt a physical friction grasp — bounded experiment, negative result

One controlled variable, three clean-restart runs, as instructed, before concluding a friction grasp was not achievable in this sim in the time available.

Procedure

Block contact softened from kp=1e6/kd=1.0 to kp=5e4/kd=50.0; gripper squeeze target tested at −0.40, −0.55 and −0.70 (of a −0.70 fully-closed range). Grasp geometry held fixed at the §7 offsets. Every run started from a full sim restart and a fresh block spawn.

Verify

RunSqueeze targetGripper stallBlock held?
A−0.40−0.334No — unchanged through lift
B−0.55−0.375No — unchanged through lift
C−0.70−0.201No — unchanged through lift

Reported as a problem, per the governing instruction: softening the contact removed the disturbance symptom seen earlier (the block popping or being punted on closure) but did not produce a hold in any of the three runs. The stall position did not track the squeeze target monotonically across runs, which argues against tuning further inside this same envelope. This is the one specification goal — a rigid-body friction grasp — not achieved.

09

Simulated attachment — the mechanism actually used

Since a friction grasp was not achievable in the time available, the block is carried by an explicit, clearly-labelled scripted weld instead.

Procedure

A gz-sim-detachable-joint-system plugin in red_block.sdf, welding the block to the robot's link6 on a message to /htgpp/attach (published right after the gripper closes) and releasing on /htgpp/detach (at the place pose). Every call is logged with the literal string SIMULATED ATTACHMENT, and grasp_meta.json carries "simulated_attachment": true for every episode.

Verify

Block z: 0.0200 → 0.099 (lift) → 0.152 (transport) → 0.068 (on the plate), with dz constant through lift and transport and the ≥5 cm rise requirement from §6 satisfied. Final block pose landed inside the plate's radius and at plate-top-plus-half-block height.

Gazebo quirk found here: gripper_base is a TF/URDF frame only — the URDF-to-SDF conversion lumps it into the link6 Gazebo link, so it does not exist as a spawnable-model link name. A DetachableJoint with child_link: gripper_base accepts the attach message and silently does nothing, with no error or warning of any kind. See the upstream-bug candidate in §bugs-upstream.

10

Record twenty episodes

scripts/episode.sh/batch.sh: a per-episode clean-restart driver, matching spec §8.3's batch table.

Procedure

Per episode: kill and relaunch the whole sim stack, spawn plate and block, wait for all three controllers active, launch move_group, configure and activate episode_recorder_node, then run the sequence with --record. Up to 3 attempts per episode. Two contracts: mycobot_pick_place.yaml (front camera) for episodes 1–15, mycobot_pick_place_heldout.yaml (/synth_camera_right) for 16–20 — both add the gripper joint to observation.state/action, which the source contract in Gazebo_to_LeRobot_Pipeline does not.

Verify

20/20 episodes ended with run_exit_code=0, placed_on_plate=true, grasp_held=true, and a non-empty .mcap bag — see §11's status.sh output.

Three infrastructure bugs found and fixed during this batch, none in the spec:

  • Recorder lifecycle: episode_recorder_node is a ROS2 lifecycle node; its record_episode action does not exist until it is explicitly configured and activated. The spec's sketch (a plain ros2 run with an immediately-usable action) does not mention this.
  • Stale ros2cli discovery: the plain ros2 lifecycle set/ros2 action list commands reported the recorder node as absent even while it was demonstrably running and configured; --no-daemon --spin-time 15 forces fresh discovery and fixed it — see the upstream-bug candidate.
  • Cold-start controller races: the three ros2_control spawners (joint_state_broadcaster, mycobot_controller, gripper_position_controller) launched in parallel sometimes all time out fighting over the controller manager's lock. Fixed with a sequential-respawn fallback, one controller at a time, when the parallel launch doesn't converge within 60 s.
11

Ground-truth batch status

scripts/status.sh — not requested by the specification, added because the recording batch spanned multiple container restarts (host suspends) and self-reported progress had to be independently checkable from disk.

Procedure

Runs from the plain host shell, no attached session needed. For each of episodes 1–20 it reads grasp_meta.json's own exit-code/verdict fields and checks for a non-empty .mcap bag file — never from memory or from a previous session's notes. It also compares wall-clock time elapsed since the container started against PID 1's monotonic uptime (a clock that does not advance during a host suspend), so a suspend shows up as a gap between the two.

Verify

bash scripts/status.sh
## PASSED=20  FAILED=0  IN-PROGRESS=0  MISSING=0  (sum=20 of 20)
12

Convert to a LeRobot-layout dataset, without torch

Not in the spec at all (Part 8 assumes an existing rosetta_port/lerobot toolchain); built here because that toolchain needs torch, which this machine could not install reliably.

Procedure

scripts/port_bag.py reads each episode's .mcap bag directly with rosbag2_py, hold-aligns /joint_states to each camera frame's timestamp (matching the contract's own align.strategy: hold), and writes the documented LeRobot v3.0 layout with pyarrow (parquet) and ffmpeg (mp4) — no lerobot/torch import anywhere.

Verify

mycobot_pick_place_train (episodes 1–15, front camera): 2670 frames. mycobot_pick_place_heldout (16–20, right camera): 927 frames. ffprobe on one clip: 320×240, 174 frames, 5.8 s — matches the frame count at 30 fps exactly.

Deferred, not skipped: this has not been loaded through the real LeRobotDataset class — that check needs torch and happens on the GPU machine. See datasets/README.md for the same note kept alongside the data itself.

13

IK robustness for a manager-chosen block position

The recording batch (§10) only ever needed 9 pre-vetted block positions. A launch-file argument lets a reviewer choose any reachable position and re-run — which meant the single-pose IK path needed the same protection the batch path already had.

Procedure

The branch-consistency retry (seed from a known-good configuration, retry up to 6 times, reject any solution outside the forward-facing elbow-up branch used by every recorded episode) previously lived only in precompute_ik.py's --poses batch path. Extracted into solve_waypoints_robust() and now shared by the single-pose path too.

Verify

Explicit-position test at (0.25, 0.00): approach J1=+0.367 descend J3=-2.420 branch_ok=True — the same branch every recorded episode used. Live-detection test (no --block-x/--block-y, reading the block's actual settled Gazebo pose instead): identical result, once the timeout bug below was fixed.

Bug found and fixed: live_block_xyz() raised RuntimeError: could not read live pose of red_block: '' — not the already-documented "prints then hangs" partial output, genuinely empty. It runs right after MoveItPy's own ~90 s build; this machine's CPU load at that exact moment was apparently enough to starve the gz model subprocess past its 10 s timeout before it printed anything at all. Fixed by retrying (5×, 25 s each) instead of trusting one short timeout.

14

run_demo.py — one orchestrator behind both launch files

Ports scripts/episode.sh's proven bring-up sequence to Python, generalised for an arbitrary block position and an optional recorder, with clean process teardown.

Procedure

Bring up sim_full.launch.py (GUI or headless per argument) → poll the three controllers active, with the same sequential-respawn fallback episode.sh uses for the cold-start spawner race → spawn plate and block at the requested position → wait, then read the block's settled pose → solve IK against that settled pose, not the commanded one (§13) → bring up move_group → if record:=true, start and lifecycle-activate the rosetta recorder → run run_pick_and_place.py → print the verdict from grasp_meta.json. record:=false (the default) skips the recorder step entirely — no rosetta install needed for the common case.

Verify

Two independent full end-to-end runs (block at (0.25, 0.00), headless), each printing RESULT: motions_ok=True placed_on_plate=True grasp_held=True. Invalid attach_mode tested separately: rejected immediately with exit code 2 and the reason spelled out, before anything is launched.

Three bugs found and fixed here, all specific to running this as a launch-file child rather than a bash script (none of these existed in episode.sh, because it was never invoked this way):

  • Self-inflicted kill: the stale-process cleanup's "ros2 launch" pattern (copied from episode.sh) matched run_demo.py's own parent — because it is now itself launched by a ros2 launch process (the launch file's ExecuteProcess), unlike episode.sh, which was always invoked directly from bash. It killed its own parent within the first second of every run. Narrowed the pattern to the two specific inner launch files that actually need cleaning up (sim_full.launch.py, move_group.launch.py).
  • Timeout crashed instead of retrying: the sh() helper let subprocess.run's TimeoutExpired propagate and crash the whole script on the very first controller poll — which is expected to time out repeatedly before the sim has even started. bash's own timeout command (used throughout episode.sh) returns gracefully instead; sh() now does too.
  • Cleanup didn't actually clean up: sending SIGINT/SIGTERM to the outer ros2 launch sim_full.launch.py subprocess handle does not reliably cascade to Gazebo/move_group — confirmed directly: a first "successful" cleanup left both fully alive. ros2 launch's own signal handling appears to be what tears down its managed processes, and an externally-delivered signal to the wrapper itself doesn't trigger that. Backstopped with the same pkill patterns pkill_stale() already uses at the start of a run, now also run at the end. See the candidate upstream report in §bugs-upstream.

Verification ladder

Each rung strictly depends on the one below it. The pipeline reaches every rung the specification asked for; the one it does not reach is the crude rigid-body grasp Part 10 itself anticipated as the ceiling. Level 7 is a later addition (§13–15) the specification never asked for: a single testable entry point.

Level 0
Passed
Scene is physically valid

Block and plate spawn, settle, and are visible and correctly coloured in a saved camera frame (§2).

Level 1
Passed
Arm reaches commanded Cartesian points

IK solves on the elbow-up branch with FK-of-IK error ≈1e-7 m; the real MoveGroup action reports success for every phase of every recorded episode (§3–5).

Level 2
Stopped here
Rigid-body friction grasp holds the block

Not achieved after a bounded, three-run experiment varying contact stiffness and squeeze effort (§8). This is the one specification goal genuinely not met.

Level 3
Passed, by substitution
The block is carried and placed, verifiably

Via the simulated DetachableJoint attachment (§9), satisfying the §6 pass/fail (constant dz, ≥5 cm rise) — but this is scripted attachment, not physics, and is labelled as such everywhere it appears.

Level 4
Passed
20 episodes recorded with a truthful instruction

Every episode's bag exists, is non-empty, and its own grasp_meta.json confirms success — independently re-checkable at any time via status.sh (§10–11).

Level 5
Passed
Episodes converted to the documented dataset layout

port_bag.py, without torch (§12).

Level 6
Not attempted here
Loaded and validated through the real LeRobotDataset class

Needs torch; deferred to the GPU machine by design (§12).

Bugs worth reporting upstream

Four defects that reproduce independent of this VM — real friction in code other teams depend on. Filing the actual issues has not been done and needs a separate explicit go-ahead.

MoveItPy cannot share a process with a plain rclpy nodeNot yet filed

Candidate repo: moveit/moveit2 (moveit_py)

Symptom
Constructing moveit.planning.MoveItPy in a process where rclpy.init() has already been called (to also run a plain Node) makes the MoveItPy constructor hang indefinitely, with near-zero CPU, stuck at the same internal log line every time — reproducible across multiple attempts and a full container restart, which rules out stale DDS state. Separately, even when MoveItPy is constructed first: if the caller lets the MoveItPy instance be garbage-collected (e.g. a helper function that returns only .get_robot_model()), its destructor logs "Deleting MoveItCpp" and tears down an internal rclcpp executor/context that a separately created rclpy Node in the same process was depending on — that Node then stops receiving any further messages, silently.
Fix used here
Architectural split: precompute_ik.py imports only moveit_py, solves every waypoint needed, and exits; run_pick_and_place.py imports only rclpy and consumes the resulting JSON. The two processes never coexist.
Why it matters
Nothing in moveit_py's public API documents that it cannot coexist with independent rclpy activity in the same process, or that keeping the object alive is load-bearing for anything beyond its own use. Both failure modes are silent — a hang with no error, and a working script that quietly stops receiving messages.

ros2 lifecycle/ros2 action CLI report a running, configured node as absentNot yet filed

Candidate repo: ros2/ros2cli

Symptom
ros2 lifecycle set /episode_recorder configure and ros2 action list both reported the node/action as not found, immediately after the node's own log confirmed it had started ("Node created (unconfigured)") and while ros2 node list in the same shell showed it present. The daemon-backed default discovery appears to serve a stale cache in this environment.
Fix used here
ros2 lifecycle set --no-daemon --spin-time 15 /episode_recorder configure (and the same for activate) — forcing fresh discovery instead of relying on the background daemon's cache resolved it every time.
Why it matters
This produced a hard, unexplained failure (FATAL: RECORDER_CONFIGURE_FAILED) on a node that was demonstrably healthy, and cost real debugging time before the daemon-cache explanation was found. A stale discovery cache with no visible staleness indicator is a sharp edge for any lifecycle-node workflow driven by the CLI.

gz-sim-detachable-joint-system silently no-ops on a non-model child_linkNot yet filed

Candidate repo: gazebosim/gz-sim

Symptom
Setting <child_link>gripper_base</child_link> on a DetachableJoint plugin — a name that is a valid TF frame but, after URDF-to-SDF conversion, is lumped into the link6 Gazebo link and does not exist as its own spawnable model link — produces no error and no warning. The attach topic accepts the message; nothing attaches; the block simply does not move on lift, indistinguishable at the log level from a genuine physics failure.
Fix used here
Retargeted child_link to link6, the real Gazebo link, found by listing the model's actual links with gz model -m mycobot_320 --link.
Why it matters
This cost a full debugging cycle that looked identical to the earlier, genuine friction-grasp failure (§8) — both present as "the block didn't move." A link-name validation error at plugin load time (the same information gz model --link already prints) would have caught this immediately instead.

An externally-delivered signal to a ros2 launch process does not reliably shut down what it managesNot yet filed

Candidate repo: ros2/launch or ros2/launch_ros

Symptom
Sending SIGINT, then on timeout SIGTERM/SIGKILL, to a Popen handle for ros2 launch gazebo_to_lerobot_bringup sim_full.launch.py (started as a subprocess of §14's orchestrator, itself running as a different launch file's ExecuteProcess) reported the process as exited cleanly — but Gazebo and move_group, the processes that inner launch file was managing, were still fully alive afterward, confirmed directly via pgrep. Interactive Ctrl+C on a foreground ros2 launch tears everything down correctly; a signal delivered programmatically to the process object apparently does not reach the same internal shutdown path.
Fix used here
Backstopped with an explicit pkill against the specific process patterns (gz sim, move_group, the inner launch files) after the signal-based attempt, rather than relying on ros2 launch's own cascade.
Why it matters
Any orchestration that nests a ros2 launch invocation inside another script or launch file — not an exotic pattern, and exactly §14's design — can leak Gazebo/node processes silently unless the caller independently tracks and kills what it started.

What this does not prove

Restating spec Part 10 in full, and adding what changed.

  • The carried block is not a physical grasp of any kind. This is stronger than the spec's own caveat (crude rigid-body contact) — even rigid-body contact could not be made to hold in the time available (§8). Any model trained on this data learns "approach, close near the block, carry it, open," not the physics of grasping.
  • Sim-trained data carries a visual domain gap, unchanged from the spec: Gazebo's renderer differs from a real camera, and this project's own DREAM result (10.9%→91.6% real detection only after mixing in real data) is direct evidence that synthetic-only training degrades badly on real images.
  • Scripted motion is not demonstration quality, unchanged from the spec: a human teleoperator produces natural correction and hesitation; this script produces the same trajectory shape every time, varying only the target position.
  • Twenty episodes is not a training set, unchanged from the spec: the community figure for fine-tuning is 100–500 per task. This is a smoke test with real semantics, not a dataset ready for training.
  • Not yet loaded through the real LeRobotDataset class (new, §12) — the on-disk layout is written to the documented spec but not proven to load until that check runs on a machine with torch.

What this does prove, precisely: the pipeline can produce structurally sound, self-verifying, task-grounded episodes with a truthful instruction, entirely headless, on hardware with no GPU at all — and it surfaces, honestly, that the grasp itself is not yet physical. That was worth establishing before any real-robot recording session is planned.

Manual execution, start to finish

Every command a person would type, in order, to reproduce one recorded episode by hand — consolidating the Procedure panels above into a single walkthrough. All of it runs inside the gazebo_to_lerobot container (docker exec -it gazebo_to_lerobot bash), with source /opt/ros/jazzy/setup.bash; source /workspace/install/setup.bash first in every new shell.

# 1. Bring up the sim stack and wait for controllers
ros2 launch gazebo_to_lerobot_bringup sim_full.launch.py &
until ros2 control list_controllers | grep -q "mycobot_controller.*active"; do sleep 5; done

# 2. Spawn the scene
ros2 run ros_gz_sim create -world empty -file models/plate.sdf -name plate -x 0.20 -y -0.15 -z 0.044
ros2 run ros_gz_sim create -world empty -file models/red_block.sdf -name red_block -x 0.25 -y 0.0 -z 0.0205
sleep 20   # let it settle
gz model -m red_block -p   # confirm it settled near (0.25, 0.00, 0.02)

# 3. Solve IK offline (moveit_py only, no rclpy)
python3 scripts/precompute_ik.py --block-x 0.25 --block-y 0.00

# 4. Bring up MoveIt2's move_group and wait for it to be ready
ros2 launch mycobot_moveit_config move_group.launch.py &
# wait for "You can start planning now!" in its log

# 5. Start the recorder and bring it to the active lifecycle state
ros2 run rosetta episode_recorder_node --ros-args \
  -p contract_path:=contracts/mycobot_pick_place.yaml \
  -p bag_base_dir:=/tmp/my_episode/bag &
ros2 lifecycle set --no-daemon --spin-time 15 /episode_recorder configure
ros2 lifecycle set --no-daemon --spin-time 15 /episode_recorder activate

# 6. Run the sequence (plain rclpy, no moveit_py)
python3 scripts/run_pick_and_place.py --record \
  --prompt "pick up the red block and place it on the plate" \
  --log /tmp/my_episode/grasp_log.csv --meta /tmp/my_episode/grasp_meta.json

# 7. Read the verdict
cat /tmp/my_episode/grasp_meta.json   # placed_on_plate, grasp_held, simulated_attachment

For the full 20-episode batch instead of one episode: bash scripts/batch.sh 1 20 does all of the above per episode, from a clean sim restart, with up to 3 retries each; bash scripts/status.sh (run from the plain host shell) reports ground truth on how far it got.

To convert recorded bags into the dataset: python3 scripts/port_bag.py --out <path> --indices "1 2 3 ... 15", reading directly from each episode's bag, no lerobot package needed.

Running the launch files instead, by hand

Everything above (steps 1–7) is what §14's run_demo.py now does automatically. To run it via the launch files instead:

# Copy the new files into the container if you haven't already (same convention as every other script here)
docker cp scripts/run_demo.py gazebo_to_lerobot:/workspace/htgpp/run_demo.py
docker cp scripts/precompute_ik.py gazebo_to_lerobot:/workspace/htgpp/precompute_ik.py
docker cp launch gazebo_to_lerobot:/workspace/htgpp/launch

# Headless, exits with a pass/fail code -- run this one to just check it still works
docker exec -it gazebo_to_lerobot bash -c '
  source /opt/ros/jazzy/setup.bash; source /workspace/install/setup.bash
  ros2 launch /workspace/htgpp/launch/pick_and_place_no_gui_demo.launch.py
  echo "exit code: $?"'

# With the GUI (needs an X/Wayland display reachable from the container -- not this machine)
docker exec -it gazebo_to_lerobot bash -c '
  source /opt/ros/jazzy/setup.bash; source /workspace/install/setup.bash
  ros2 launch /workspace/htgpp/launch/pick_and_place_demo.launch.py'

# Try a different block position
ros2 launch /workspace/htgpp/launch/pick_and_place_no_gui_demo.launch.py block_x:=0.28 block_y:=0.05

# See every argument and its description
ros2 launch /workspace/htgpp/launch/pick_and_place_no_gui_demo.launch.py --show-args

How to read the result. The launch prints a boxed RESULT line near the end:

[demo 14:19:10] ============================================================
[demo 14:19:10] RESULT: motions_ok=True placed_on_plate=True grasp_held=True
[demo 14:19:10] carry mechanism: SIMULATED ATTACHMENT (gz DetachableJoint), NOT a physical grasp
[demo 14:19:10] ============================================================

All three of motions_ok, placed_on_plate and grasp_held must be True for a pass. The same fields are also written to demo/grasp_meta.json under the project root, so a script can check the result without parsing log text:

cat /workspace/htgpp/demo/grasp_meta.json
# { "placed_on_plate": true, "grasp_held": true, "simulated_attachment": true, ... }

Checking attach_mode validation. Any value other than simulated must fail immediately, before anything is launched:

ros2 launch /workspace/htgpp/launch/pick_and_place_no_gui_demo.launch.py attach_mode:=friction
# -> "attach_mode: only 'simulated' is currently supported. ..." exit code 2, nothing started

Confirming a clean teardown. After the launch exits (or after Ctrl+C on the GUI variant), no simulation processes should remain:

docker exec gazebo_to_lerobot bash -c 'pgrep -af "gz sim|move_group|sim_full"'
# nothing printed = clean. Entries tagged <defunct> are already-dead zombie
# processes waiting to be reaped -- harmless, hold no resources, safe to ignore.

Running this for the first time on a fresh container? §10's pre-solved waypoints/ directory isn't needed here: §13's live-detection path solves IK for wherever the block actually lands, every time, for any position you pass.
