Overview & architecture

Two Docker containers that never run at the same time, and why.

This pipeline turns the two mcap bags already recorded in the Gazebo_to_LeRobot_Pipeline sandbox into an RLDS/TFDS dataset in OpenVLA's expected Open-X Embodiment (OXE) layout, then registers that dataset with OpenVLA itself. It reuses moojink/rlds_dataset_builder — a fork of the standard OXE dataset-builder scaffold maintained by Moo Jin Kim, OpenVLA's first author, which makes it a safer bet for staying aligned with what OpenVLA's own dataloader expects than the (functionally identical) upstream kpertsch/rlds_dataset_builder.

The ROS2 side (reading mcap bags, computing forward kinematics) and the RLDS side (TensorFlow, TFDS) have nothing to do with each other technically, and pinning both into one container would mean carrying ROS2 Jazzy, MoveIt2, and TensorFlow 2.13 simultaneously — real memory pressure on this VM. So this pipeline runs across two containers that are never both running at once: gazebo_to_lerobot (already existing, ROS2 Jazzy + MoveIt2) does the extraction and FK; rlds_builder (new, Python 3.9 + TensorFlow 2.13.0) does everything from tfds build onward. They talk to each other only through files — the .npy episodes the extraction step writes.

The resource ceiling that shaped this pipeline, same as Gazebo_to_LeRobot_Pipeline's: ~4.8 GB RAM, CPU-only. It directly caused the conda→pip pivot in step 1, the container mutual-exclusion rule above, and the decision to skip the Universal Sentence Encoder language embedding entirely in step 8 — each documented at the point it happened below.

The pipeline, step by step

Same convention as the Gazebo_to_LeRobot_Pipeline runbook: every step pairs how it's done with the concrete check that proves it worked.

01

Set up the converter environment

A container with the fork's exact pinned dependencies — Python 3.9, TensorFlow 2.13.0.

Procedure

First attempt: conda env create -f environment_ubuntu.yml inside a continuumio/miniconda3 image, exactly as the fork's README instructs. This was killed by the host's low-memory guard — conda's SAT solver loads full channel repodata into memory before installing anything, expensive even for a small, fully-pinned env.

Recovered by dropping conda entirely: extracted the same pinned versions straight from the yml's own pip: section (97 packages, confirmed no stray CUDA deps) into a requirements.txt, and built python:3.9-slim + pip install --no-deps instead, split across several small RUN layers (3 of them isolating the heaviest wheels — tensorflow, tensorflow-datasets, apache-beam — each in its own cached layer) so a build that dies partway doesn't lose everything.

Verify

  • docker images lists the built image.
  • python3 -c "import tensorflow as tf, tensorflow_datasets as tfds; print(tf.__version__, tfds.__version__)" prints 2.13.0 4.9.2 with no import errors.
02

Dummy-data smoke test

The fork's README says explicitly to run this before touching real data.

Procedure

cd rlds_dataset_builder/example_dataset
python3 create_example_data.py
tfds build

This step also downloads a Universal Sentence Encoder from TF-Hub (for the example's language_embedding field) — real memory pressure, mitigated by retroactively capping the running container (docker update --memory=2g --memory-swap=3g) mid-build.

Verify

  • tfds build completes, writes to ~/tensorflow_datasets/example_dataset/1.0.0.
  • tfds.load("example_dataset", split="train") round-trips: 10 steps/episode, correct (64,64,3) images, (10,) action, readable language_instruction.
03

Inspect the source bags

Two rosetta-recorded mcap bags, still inside the (stopped, not removed) gazebo_to_lerobot container.

Procedure

docker start gazebo_to_lerobot, then ros2 bag info on each of /workspace/datasets/bags/{1789171382_864718428, 1789172093_868865993}. Critically, cross-checked each message's own header.stamp (simulation time) against the bag's wall-clock recording duration.

Verify

The mismatch itself was the finding: episode 1 spans 66.15 s wall-clock but only 6.50 s of simulation time — roughly a 10× real-time-factor slowdown. Camera frames land at ~10 Hz sim-time (not the 30 Hz the original contract assumed), joint states at ~100 Hz sim-time (matching the controller's configured rate). This directly determined step 4's sync rate and confirmed sim time, never bag-receive time, is the only clock that means anything here.

04

Extract & time-sync topics

One pass per bag: collect /joint_states and the camera topic, interpolate joints onto each camera frame.

Procedure

extraction/extract_episodes.py, run inside gazebo_to_lerobot. Reads both topics via rosbag2_py.SequentialReader, sorts by each message's own header.stamp, then for every camera frame's timestamp linearly interpolates every joint angle from the two bracketing /joint_states samples (holding at the ends, never extrapolating). Never the reverse — images are held at their native timestamp, joint angles are the ones interpolated, because you can interpolate numbers but not images.

Verify

  • Output step count matches camera frame count exactly: 66 and 52 for the two episodes.
  • No NaNs in any interpolated joint value.
05

Forward kinematics via MoveIt2 RobotState

Per-timestep end-effector pose from the interpolated arm joint angles.

Procedure

moveit_py's RobotState.get_pose("link6"), built once per process from the existing mycobot_moveit_config (arm group, base→link6) — heavier than a raw KDL chain, but the same kinematic model the robot already plans with. MoveItPy's constructor refuses to start without a loadable planning pipeline even for pure FK (see the upstream issue below), so a full OMPL config had to be assembled just to satisfy that requirement.

Verify

Independently reconstructed the same base→link6 pose by chain-multiplying the bag's own per-joint /tf transforms (what Gazebo/robot_state_publisher actually computed live) for the same joint configuration:

MoveItPy FK:      pos (0.009739, -0.178012, 0.487297)  quat (-0.046497, 0.679719, -0.553414, 0.479118)
/tf chain (bag):  pos [0.009739, -0.178012, 0.487297]   quat [-0.046497, 0.679719, -0.553414, 0.479118]

Matches to 7 decimal places — not a plausibility check, proof the FK path reproduces the exact kinematics the robot used.

06

Position/rotation deltas & gripper channel

Assemble the 8-dim state and 7-dim action vectors from consecutive poses.

Procedure

State (8-dim): [x, y, z, qx, qy, qz, qw, gripper] — absolute pose + the gripper_controller joint's interpolated position. Action (7-dim): [dx, dy, dz, droll, dpitch, dyaw, gripper] — position delta to the next step, rotation delta as small-angle Euler xyz (R_i⁻¹ R_{i+1}), and gripper as an absolute value on this step, not a delta — matching the same convention OpenVLA's own bridge_oxe_dataset_transform uses. Last step of each episode gets a zero pose-delta (no "next" state exists) rather than extrapolating.

Verify

  • No NaNs in 118 total timesteps across both episodes.
  • Position-delta magnitudes: 0 – 0.0042 m per step — sane for smooth 10 Hz teleop, no outliers.
  • Correction made here: an earlier claim this session that "the gripper never moves" (based on a different, constant command topic) turned out wrong once the actual per-frame data was extracted — episode 0's gripper channel swings 0 → -0.70, a real, decisive transition. See step 9.
07

Image processing

Decode, correct colour order, resize+center-crop to 224×224.

Procedure

The CompressedImage.format field reads 'rgb8; jpeg compressed bgr8' — ROS's compressed_image_transport recording that it converted to BGR8 before handing pixels to OpenCV's BGR-native JPEG encoder. So cv2.imdecode's output is genuinely BGR, and cv2.cvtColor(..., COLOR_BGR2RGB) is applied unconditionally (asserted on that exact format string, not a soft guess). Resize: scale shortest side to 224, center-crop the other to match, INTER_LINEAR.

Verify

The scene turned out to be nearly grayscale, so a visual before/after check was inconclusive on its own (a B/R swap is invisible with no red or blue in frame) — the format-string reasoning above is what actually settled it, backed by the format field's own literal content, not eyeballing.

08

Write the dataset builder, run the real build

gazebo_to_lerobot_mycobot_dataset_builder.py, modeled on example_dataset.

Procedure

cd rlds_dataset_builder/gazebo_to_lerobot_mycobot
tfds build --overwrite

Same FeaturesDict shape as the example, minus wrist_image (single camera) and minus language_embedding — deliberately dropped: it needs the same Universal Sentence Encoder download that stressed memory in step 2, and OpenVLA's own OXE transform functions only ever consume the raw language_instruction text, never a precomputed embedding, so it isn't load-bearing here.

Verify

  • Build completed in ~2.4 s (no heavy download this time) — 2 examples, dataset_size=1.02 MiB.
  • tfds.load round-trip matches the extraction output exactly: 66/52 steps, correct state/action shapes, correct is_first/is_last flags, matching instructions.
09

Validate the dataset

The fork's own visualize_dataset.py, plus the four specific checks below.

Procedure

visualize_dataset.py calls plt.show(), which needs a display this headless container doesn't have. Ran the real, unmodified script via a small runpy wrapper that only monkeypatches plt.show() to save each open figure to PNG instead of blocking — the validation logic itself untouched.

Verify — the four checks

  • Images show the motion: yes — 6 evenly-sampled frames show the arm sweeping, and the gripper fingers visibly open between frame 4 and 5/6.
  • Action histograms look sane: yes — all 6 pose-delta dims tightly concentrated near zero, no NaNs, no outlier spikes.
  • Gripper dimension actually switching: yes — clearly bimodal (cluster near 0, cluster near -0.70, almost nothing between), matching the visual open/close transition.
  • Instructions match episodes: yes, deliberately conservative — both labeled "scripted joint trajectory, no object, mechanics test," and nothing in the images or data contradicts that.
10

Register with OpenVLA

Three files: configs.py, transforms.py, mixtures.py.

Procedure

  • configs.py — OXE_DATASET_CONFIGS["gazebo_to_lerobot_mycobot"], modeled on berkeley_autolab_ur5 (the existing entry whose single state_obs_keys: ["state"] pattern matches ours): StateEncoding.POS_QUAT, ActionEncoding.EEF_POS.
  • transforms.py — gazebo_to_lerobot_mycobot_dataset_transform: our data is already in canonical shape, so the only real work is normalizing the gripper (raw URDF joint radians, limits [-1.20, 0.10]) into this file's "+1=open, 0=closed" convention, using the real URDF limits rather than the 2 episodes' own observed range.
  • mixtures.py — "gazebo_to_lerobot_mycobot": [("gazebo_to_lerobot_mycobot", 1.0)], matching the pattern OpenVLA uses for its own LIBERO/droid_wipe fine-tuning datasets.

Verify

Importing normally cascades into OpenVLA's full torch/transformers stack (see the upstream issue below) — avoided that by stubbing the prismatic.* package hierarchy in sys.modules with correct __path__s, so Python resolves the real files without executing the heavy chain. Ran the actual registered function against a real batch from the built dataset:

input  gripper (state) range: -0.700 → 0.000
output gripper (state) range:  0.077 → 0.615   # normalized per URDF limits
All assertions passed: gripper normalized into [0,1], all other columns bit-for-bit unchanged.

Also confirmed present and internally consistent across all three registries, and that the registered function is literally the one written (identity-checked).

Issues worth reporting upstream

Unlike the Gazebo_to_LeRobot_Pipeline runbook's two correctness bugs (silent wrong output), this session's findings are real friction/architecture issues — reproducible, but nothing here produced a wrong result once worked around. Filing has not been done and needs a separate explicit go-ahead.

MoveItPy has no lightweight path for pure FK/RobotState useNot yet filed

Candidate repo: moveit/moveit2 (moveit_py)

Symptom
Constructing moveit.planning.MoveItPy with only robot_description/robot_description_semantic/robot_description_kinematics params — everything actually needed for RobotState.get_pose() FK — fails outright: RuntimeError: Failed to load planning pipelines from parameter server. There's no documented way to get a bare RobotModel/RobotState without also supplying a fully loadable OMPL planning pipeline config, a controller manager, and a planning scene monitor — none of which pure FK ever touches.
Workaround used here
Assembled a full, working ompl_planning.yaml-equivalent params dict (request/response adapters, planner configs) purely to satisfy the constructor, even though no planning was ever performed.
Why it matters
Every project needing standalone FK via the "real" MoveIt2 kinematic model (as opposed to raw KDL) hits this same wall. A lighter constructor path, or a documented minimal-viable planning-pipeline stub, would remove a real barrier to a legitimate, common use case.

Importing OpenVLA's OXE dataset-registration modules requires the full training stackNot yet filed

Candidate repo: openvla/openvla

Symptom
prismatic/__init__.py unconditionally imports .models, which cascades into huggingface_hub → draccus → eventually torch/transformers (multi-GB) — as a side effect of importing any submodule of the prismatic package, including prismatic.vla.datasets.rlds.oxe.{configs,transforms,mixtures}, which are themselves pure-TensorFlow and have zero dependency on the model-loading code.
Workaround used here
Stubbed the prismatic.* package hierarchy in sys.modules with empty placeholder modules carrying the correct __path__, so Python's import machinery resolves the real OXE files on disk without ever executing prismatic/__init__.py.
Why it matters
Anyone wanting to register or test a new OXE dataset — the officially documented first step of adding custom data to OpenVLA — currently has no way to do so without installing the entire multi-GB training dependency stack first. Making the heavy imports lazy (or splitting dataset-registration into a package that doesn't import .models) would let that documented workflow actually be lightweight.

Git & reproducing this from scratch

Local git repo, not yet pushed anywhere — sharing it is a deliberate future step.

Repo root ROS2_to_RLDS_Conversion_OpenVLA/, branch main, commit e79e597 (18 files, ~152 KB). Two cloned upstream repos are gitignored wholesale rather than tracked, since each has its own separate git history and tracking them as regular files/subtrees would create nested-repo ambiguity: rlds_dataset_builder/ and openvla/. Our own additions/edits inside each live under overrides/ instead of duplicating either tree — the same pattern the Gazebo_to_LeRobot_Pipeline runbook uses for its own vendored code.

A teammate reproducing this from scratch needs, in order:

git clone <this repo> && cd ROS2_to_RLDS_Conversion_OpenVLA

# 1. re-clone the two upstream repos (step 1, step 10)
git clone https://github.com/moojink/rlds_dataset_builder.git
git clone --depth 1 https://github.com/openvla/openvla.git

# 2. re-apply our overrides on top
mkdir -p rlds_dataset_builder/gazebo_to_lerobot_mycobot
cp overrides/rlds_dataset_builder/gazebo_to_lerobot_mycobot/* rlds_dataset_builder/gazebo_to_lerobot_mycobot/
cp overrides/openvla/prismatic/vla/datasets/rlds/oxe/* openvla/prismatic/vla/datasets/rlds/oxe/

# 3. build the rlds_builder container (step 1)
docker/run.sh

# 4. re-extract the 2 episodes (step 4) -- needs the gazebo_to_lerobot container
#    and its still-existing bags at /workspace/datasets/bags/, or freshly
#    recorded ones -- then place the resulting .npy under
#    rlds_dataset_builder/gazebo_to_lerobot_mycobot/data/train/
docker cp gazebo_to_lerobot:/workspace/... extraction/extract_episodes.py ...

# then steps 8-10 as documented above
